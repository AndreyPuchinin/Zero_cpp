ТЕРМИНЫ, СОСТАВЛЯЮЩИЕ ЧАСТИ И ПРОЦЕСС ИХ ОБРАБОТКИ:

Ядро Зеро - самый внутренний механизм Ядра. Полностью теоретизирован, исключены абсолютно полностью все конфликты, реализуется прямо сейчас.

-входная строка (всегда в текстовом формате той или иной кодировки, одинаковой для всей работы вплоть до конца алгоритма)
--меняется посредством алгоритма, ищущем в строке вхождения элементов БД - “Библиотеки Карточек”

-Карточки с 
--именем (пустая или непустая строка в текущей кодировке. Уникальна в рамках одной библиотеки Карт)
--значением (пустая или непустая строка, см. ниже. Уникально в рамках одной библиотеки Карт)
--ссылками между картами (упоминание полного имени другой карты в имени или значении текущей)
---имя ссылки (первичное найденное и заменяемое в строке значение)
---значение ссылки (эволюционирующее)
---тип ссылки (типы ссылок различаются по финальным значениям после последней замены: разные финальные значения - разные типы)
--значением одного из 5-ти типов: 
---обычная (методом исключения - ни одно из ниже перечисленных) 
---самоссылка (сжималка: имя полностью и точно входит в собственное значение хотя бы один раз), 
---шаблонная (переставлялка: есть, как минимум, одна ссылка одинакового типа и в имени и в значении шаблона), 
---шаблонная самассылка (сжималка-переставлялка: обладает свойствами и того, и другого), 
---айдишник (более сложная переставлялка-разрешение конфликтов в случае неуспеха шаблонной замены -  “коллизий”); 
---айдишник-самоссылка
---айдишник-шаблон
---айдишник-самоссылка-шаблон

-Библиотека - набор карточек (один объект Менеджера Карт содержит только одну библиотеку! При необходимости новой требуется создавать новый объект класса Менеджера Карт - см. ниже)
--порядок добавления карт и их значений значения не имеет!

-Классы внутри Ядра:
--Карточка - все типы значений указываются явно, но класс исключает и предупреждает какие-либо ломания для абсолютно любого ввода (всегда в формате текстовой строки избранной кодировки для Ядра)


--Менеджер Карт:
---распределяет типы вводимых значений автоматически или проверяет корректность явного указания типа,
----в порядке, указанном выше
----если тип указан явно, сначала проверяется он, а затем в случае несовпадения - все с начала. Это экономит время проверок на масштабе больших библиотек Карточек в случае верного указания пользователем типа вводимого значения
----для айдишника требуется создать отдельный объект Парсера (см. ниже) прямо в Менеджере карт:
-----выделяем все шаблоны (все шаблонные значения и соответствующие им имена их Карточки)
-----парсим каждое из них. Отрабатывает лишь этап прямых обычных Свапов Парсера (см. ниже)
-----после каждого парсинга проверяем, не образовалось ли после замен в парсящеймся имени или значении полного и точного вхождения значения претендента на значение-айдишник
------в случае, когда образовалось
-------объявляем претендента на значение-айдишник в самом деле официально айдишником
-------заменяем вхождение значения, ставшего официально айдишником, в текущем парсящемся имени или значении - на такое же, но с исключенным из этого отрывка именем карточки с данным значением, ставшим айдишником
-------дополняем во вспомогательные служебные поля этого текущего имени или значения информацию о принадлежности данному отрывку - стертого из него имени карточки с данным значением, ставшим айдишником
-------в дальнейшем Парсер будет искать подстертое значение, но будет помнить принадлежащем ему имени айдишника, делающее данное подстертое значение уникальным относительно других таких же, но с другим подстертым именем айдишника
---определяет связь между картами:
----заполняет дополнительные информационные поля имени и значения:
-----имена ссылок каждого типа
-----позиции каждой ссылки каждого типа в имени и значении
---выявляет ошибки при вводе библиотеки в следующем наиболее оптимальном порядке
----значение не должно совпадать с именем текущей карты
----значение не должно содержаться в имени текущей карты
----имя должно быть уникальным в рамках библиотеки
----значение так же должно быть уникальным в рамках библиотеки
-----последние две проверки сёрчат все карты библиотеки до тех пор, пока не найдется ошибка или не достигнется конец всех карт библиотеки
----не должно быть циклических зависимостей разной сложности, приводящих к бесконечным заменам на любом их этапе! (см. мой алг обхода бандажей! ПОМЕТКА: в нем отсутствует некая одна из дополнительных оптимизаций)
--использует объект Логгера, переданный извне (из класса-оболочки “Зеро”) и пишет в него первым всю информацию об успешно внедренных в текущую библиотеку карт. В т.ч. дополнительную служебную информацию о них

--Парсер - парсит входную строку или значения карт и их имена. Имеет этапы эволюции строки (замен - типы свапов). Замены производятся, последовательно чередуя типы Замен. В процессе каждого типа 
---бегунок бежит по входной строке слева направо, 
---ищет ближайшее наидлинное подходящее значение (выбор приоритета между близостью и длинной - чуть более сложный отдельный алгоритм) 
---заменяет его на имя найденной карты
---перемещает бегунок на конец замены
---и продолжает поиск, пока не конец строки
---по достижению конца, происходит проверка:
----если была произведена хотя бы одна замена в текущем типе Свапа, алгоритм повторяется с начала строки
----если не было ни одной замены в текущем типе Свапа, алгоритм переходит к следующему типу Свапа, если он есть, или выдает
-----первую версию строки (в любом случае)
-----версию строки после последней успешной замены (не коллизии, в любом случае)
-----пользовательскую строку (если была коллизия)
----такой алгоритм пробега по строе позволяет предупредить бесконечные замены (см. мой файл с обходом бандажей)
----после последнего типа Свапа строка может быть пропаршенна заново с самого начала по желанию пользователя (может быть установлено автоматом). Тогда это новая итерация всего Алгоритма Парсера. Именно это позволяет проекту в дальнейшем заиметь Полноту по Тьюрингу
-----если пользователь указал режим парсинга заново, пока не условие, имеет место быть проблема останова, решаемая Ограничением Времени Жизни процессса
--Типы Свапов:
---простые прямые обычные (ищутся обычные значения)
---простые прямые самоссыльные (в т.ч. по самоссылкам-шаблонам, айдишникам-самоссылкам и айдишникам-самоссылкам-шаблонам)
---шаблонные (в т.ч. по самоссылкам-шаблонам и айдишникам-самоссылкам-шаблонам)
---в случае коллизии - попытка айдишных
---в случае успеха - обратные (заменяем значения всех ссылок после перетасовки их шаблонами на их имена - первичные значения)
–Использует объект Логгера, переданный извне (из класса-обертки “Зеро”), и документирует все свапы в него после информации от Менеджера Карт

--Логгер - создает json-лог-файл
---все, что связано с json’ом - работа Логгера!
---содержит в себе локальную переменную для формирования наполнения json’а
---имеет функцию передачи-заполнения этой локальной переменной
---имеет функцию записи в файл (В ПОСЛЕДНИЙ МОМЕНТ!!)
---имеет функцию вывода локальной переменной (в т.ч. её ранних версий, еще не успевших попасть в файл)
---и отдельно вывода содержимого итогового файла (может оказаться пустым - это нормально!)

--Зеро
---создает объекты Менеджеров карт для каждой библиотеки
---создает объект Парсера
---создает объект Логгера и передает его последовательно в объекты Менеджера Карт и Парсера
---вызывает warp_drive() - функцию запуска анализа Зеро входного json-файла, генерации лог-файла и (возможно) модификации карт в указанных библиотеках с помощью Фильтров

-Фильтр - применяемая библиотека к данным. Данные могут быть, как входными (входная строка), так и внутренними - Карточками из других библиотек

–Коллизии при заменах строки (её эволюции алгоритмом Парсера Зеро) - неизвестность, не разрешенная неопределенность необходимости обратной замены на одно из двух или более имен ссылки при обратных заменах

-Json-лог/управляющий-файл - полная дебаг-информация для данных подключенных библиотек, входной информации и её преобразований

-Диалект Зеро - программа на Зеро, способная обрабатывать пользоватльский ввод своим исключительно уникальным образом

Подход к ТЕСТАМ:

Метод ровно обратен TDD - тесты пишутся не раньше кода, а в последний момент:
-метод представляет авто-генерацию тестов:
—ожидаемый вывод
—получаемый результат первичной механики тестируемого объекта
-ожидаемый вывод оперирует лишь символами
-механика объекта оперирует смыслами

-Если заменить символ Правды и символ Неправды друг на друга в ожидаемом выводе, изменится лишь символьное их обозначение, но не первичное поведение тестируемого объекта (все равно, что всех "Кошек" в математике обозвать "Собаками", а всех "Собак" - "Кошками")

-Глобальная тестируемая функция Метода, генерящая тесты, принимает параметры, указывающие на свойства тестов (например, число корректных символов Правды и число некорректных символов Неправды, подаваемых в итоговый сгенерированный тест)

-Можно вызывать Глобальную тестируемую функцию Метода и проверить потенциально ВООБЩЕ ВСЕ случаи на свете, предполагаемые контекстом механики поведения тестируемого объекта

-Глобальная функция должна стремиться к тому, чтобы способствовать процессу "выправления" устройства механики тестируемого объекта. А именно, каждый генерируемый тест должен совпадать с ожидаемым результатом

—Если Глобальная функция Метода имеет хотя бы один сгенерированный не прошедший тест в конечном итоге (после финального выправления первичной механики поведения тестируемого объекта), это должно быть учтено
—-либо глобально (но тогда есть риск забыть или даже не узнать о том, что нужно учитывать это глобально, например, наложение табу на использование такого случая с такими тестируемыми параметрами)
—-либо локально, что предпочтительнее, причем, вероятно, абсолютно.

-Все это позволяет Глобальной функции Метода предоставить возможность даже не просто к авто-тестирования (автоматической генерации ряда тестов), - а еще и потенциальной возможности авто-"выправления" поведения тестируемого объекта! Впрочем, эта технология еще должна доразработаться.

ДИАЛЕКТ ЗЕРО (внутренний, используемый Зеро самим для себя - низкоуровневый код, в который может приводиться речь пользователя на поздних этапах разработки. Это решает проблемы читаемости и применения сложных конструкций ради универсализации применимости этого кода внутри авто-генерируемой самим Зеро библиотеки):

Любая лексема является строкой-элементом, которое можно положить во множество. Даже знаки равенства! Лексемы содержатся в стеке структуры лексем в формате json.


# - комментарий

Пример:

...  # комментарий строки


{} - упорядоченное множество
() - неупорядоченное множество без повторений элементов. Важно, что предпринимается попытка воспринимать группирование тоже как такое множество!


= - императивный вызов Зеро, вопрос ему: "чему равно?" Зеро может формулировать такие вопросы сам себе и сам на них же отвечать. Например, в случаях

—абстрагирования
—прогрессивной и регрессивной дефрагментации
—авто-заменах при вычислении или комментарии (в последнем случае без выигрыша чего-либо)
—тактическом и стратегическом планировании

== - как раз комментарий, банальная замена без выигрыша, абсолютно равносильная

:= - декларативное присвоение

:+= / :-= / :*= / :(/=) работает так же, как и в прочих ЯП, но продолжается и в 

(:^=) / (:(*2+1)=) /

( {set1,set2,set3}(:(:=)=){1,{2,2},(3,3)} )  ==

== ( (set1:=1) , (set2:={2,2}) , (set3:=(3)) )

ПРИМЕР:

( (:=)==(=) ) - все равно в данном оторванном контексте  (у меня уже встретилось в сложном примере) что вызвать присвоение, что задать вопрос Зеро "чему оно равно?"


|()| - размер множества ()

|{}| - размер множества {}


( set(x)set2 ) == ( (set1)(set2) ) - декартово произведение set1 и set2, заключающееся в {}


* - арифметическое произведение

Пример:

set:={1}
N:=5
(set:=set*N) == (set:={1,1,1,1,1})


, - разделитель элементов.

Пример:

(,)(a,b) = {aa,ab,ba,bb}


^ - декартова степень

Пример:

set:={...}
set:=(,^|set|)(set) == (set)^(|set|+1)
set:=(,^(|set|-1))(set) == (set)^|set|


/ - исключение из множества

Пример:

x := {L,M,R}
y := {D,E,U}
z := {B,S,F}

axes := {x,y,z}

elements := x(x)y(x)z \ ( x^2 , y^2 , z^2 )  # исключаем из генерации элементы типа UUL, LRD , ...  # НО! Это не исключит ULU! Тут нужен другой механизм - см. ниже


(⭠^N)self - ссылка на элемент N шагов назад в стеке структуры элементов на том же уровне глубины, если он не первый (иначе выныриваем на 1 уровень вверх в элемент, содержащий данный как дочерний) После выныривания - та же логика.

(⭡^N)self - ссылка на элемент N шагов вверх в стеке структуры элементов

(⭣^N)self - ссылка на элемент N шагов вглубь в стеке структуры элементов. Первый элемент берется текущим, все последующие - первыми на каждом дочернем уровне (если только ссылка не смещалась другими командами навигации ссылки)

(⭢^N)self - ссылка на элемент N шагов вперед в стеке структуры элементов. На том же уровне глубины, если он не последний.

Если ссылка уходит далее имеющихся элементов в строке (вправо или влево), текущий self в текущем контексте == первый для ⭠ или последний для ⭢ элемент строки. НО! если поместить этот объект во внешний контекст, перебор ссылок компенсируется за счет предыдущих элементов внешнего контекста! Опять же, возможна ситуация, когда и в этом случае ссылка обрубится на начале, но тогда можно снова поместить её в еще более внешний контекст, ...

Пример:

( elements:=⭠self ) == ( elements:=elements )

axe := {...}
dim := 100
axes := {axe(^)dim}
elements := ( axes(.^|⭡⭠self|) == axes(.^|axes|) )

els_by_layers := ( elements(x)(,^|⭡⭠⭠self|) == elements(x)(,^|elements|) ) 
# {{U,R,F},{U,R,S},{U,R,B}, ...} - элементы с повторениями слоев с одной оси в одном эле-те
Els_by_ls_N:=|elements|
self_templ = .^(2*Els_by_ls_N)self
(elements.:=self_templ)\(,)  # {{URF},{URS}, ...} == elements


set. - распаковка множества set

Пример:

set:={el1,el2}
set:={set,set}
set. == {el1,el2,el1,el2}  # раскрытие подмножества вниз на уровень глубины 1

set:={el1,el2}
(set:={set,set})^2 == (set:={set,set} , set:={set,set})
set.. == {el1,el2,el1,el2,el1,el2,el1,el2} 
# раскрытие подмножества вниз на уровень глубины 2

set_deepest:={...}
set:=set_deepest
N:=...
(set:={set*N})^|set|
set(.^|set|) == {set_deepest*(N^|set|)}
