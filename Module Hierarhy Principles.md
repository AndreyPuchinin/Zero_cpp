# ПРИНЦИПЫ МОДУЛЬНОЙ ИЕРАРХИИ

## 📋 ПРИНЦИП 1: СИГНАТУРА (КОНТРАКТ) МОДЕЛИ

### Что входит в Сигнатуру?
1. **Входные параметры** и их типы
2. **Выходные параметры** и их типы

### Компактность параметров
#### ✅ ПРАВИЛО:
Параметры должны быть:
- **a) МИНИМАЛЬНЫ** - только те, что влияют на логику
- **b) МАКСИМАЛЬНО ОБЩИ** - каждый параметр общий, не специфичный

#### Пример на питоне (плохо):
```python
# ❌ Слишком много параметров, слишком специфичные
class Commutator:
    def __init__(self, left_expr, right_expr, 
                 color, position_x, position_y, 
                 font_name, font_size):
        pass
```

#### Пример на питоне (хорошо):
```python
# ✅ Минимально необходимо + максимально общие
class Commutator:
    def __init__(self, left: Expression, right: Expression):
        self.left = left
        self.right = right
```

### Методы достижения компактности:

#### a) Горизонтальное слияние
Объединить похожие параметры в один:
```python
# ❌ ДО
def move_elevator(speed, weight_limit):
    pass

# ✅ ПОСЛЕ
def move_elevator(priority):  # инкапсулирует скорость и весовой порог
    pass
```
Горизонтальное слияение следует делать **всегда** до тех пор, пока это не вредит проекту (пока новое объединение не начнет урезать инормацию)

#### b) Вертикальное слияние
Перенести усложнение логики на новый уровень:
```python
# Базовый уровень (простой контракт)
class SimpleElevator:
    def __init__(self, position: int, targets: list):
        pass

# Продвинутый уровень (тот же контракт)
class SmartElevator:
    def __init__(self, position: int, targets: list):
        # Добавлена логика: если целей нет, вернуться на базу
        pass

# Оба имеют ОДИНАКОВУЮ Сигнатуру, но разное поведение! 
# Это и дает быстрое и бзопасное изменние кода 
# вне зависимости от уровня абстракции сущености.
```
Вертикальное слияение следует выполнять **только тогда, когда это нужно** (код не должен быть перегржен Моделями, правило **компактности** рспространяется в том числе и на Модели)

### 🏗️ ПРИНЦИП 2: КАЖДАЯ МОДЕЛЬ = ОДИН ФАЙЛ

#### Где находятся модели?
📁 **Все модели** должны быть в папке `/Models/` (допустимо логическое разбиение на подпапки)

#### Пример структуры моделей в абстрактном проекте (в контексте Теории Групп и Кубика Рубика)):
```
Models/
├── Expression     (базовый класс всех выражений)
├── Literal        (литеральное - атомарное значение, например, "BL3'" для мегаминкса)
├── Commutator     (коммутатор [A,B])
├── Conjugate      (конжугат [A:B])
└── __init__       (экспорт всех моделей)
```

### Правила:
- ✅ Один файл = одна модель (позже Линковщик J-code проверит каждый файл на ошибки и сошьет их воедино)
- ✅ Модель = можно представить в виде класса, определяющего структуру данных
- ✅ Максимально компактная сигнатура (минимум максимально общих параметров)

## 🔄 ПРИНЦИП 3: ДАННЫЕ ОТДЕЛЕНЫ ОТ ПОВЕДЕНИЯ

### Данные (Models)
**Что?** Классы, определяющие структуру

**Где?** `/Models/*` - каждый класс в отдельном файле

**Пример на Python:**
```python
class Expression:
    """Базовый класс для всех выражений"""
    pass

class Literal(Expression):
    """Литеральное (атомарное) выражение"""
    def __init__(self, value: str):
        self.value = value
```

### Поведение (System Behavior)
**Что?** Функции, которые трансформируют данные

**Где?** `/Models/system_behavior` - все функции в одном файле

**Пример на Python:**
```python
def convert_to_latex(expr_str: str) -> str:
    """Главная функция оркестрации всего процесса"""
    # Валидация -> Парсинг -> Генерация LaTeX
    ...
```

### ✅ ИТОГ:
- Models: определяют **структуру, данные** (и только их)
- system_behavior: определяет **преобразования, трансформацию данных** (и только их)

## 🧩 ПРИНЦИП 4: ФУНКЦИОНАЛ РАНЖИРУЕТСЯ ПО ПРИМЕНИМОСТИ

### ❌ НЕ по уровню абстракции (как в ООП)
```
❌ НЕПРАВИЛЬНО (ООП-стиль):
BaseExpression (самый абстрактный, уровень 0)
    ↓
ConcreteExpression (более конкретный, уровень 1)
        ↓
SpecificExpression (самый конкретный, уровень 2)
```

### ✅ ПО применимости (как в Модульной Иерархии)
```
✅ ПРАВИЛЬНО (Модульная Иерархия):
Модель_1 (применима в контексте А)
Модель_2 (применима в контексте Б)
Модель_3 (применима в контексте В)

Все Модели находятся в РАВНЫХ условиях!
Это как кубики Лего - раскиданы по плоскости,
и можно взять любой кубик и положить его в любое место,
если его Сигнатура совпадает.

Характерная черта: меньше роль наследования, 
но при замене Модели А на Модель Б это можно сравнить 
с полиморфизмом в ООП 
(только в Модульной Иерархии это реализовано гораздо проще).
```

### Пример из проекта для выржажений в кубинге и Теории Групп - коммутаторов и конжугатов:
```python
Expression (контракт)
├── Literal (применима для атомарных выражений)
├── Commutator (применима для операции [A,B])
└── Conjugate (применима для операции [A:B])

Все три: Literal, Commutator, Conjugate имеют 
одинаковую Сигнатуру (контракт Expression),
поэтому они ВЗАИМОЗАМЕНЯЕМЫ!
(можно подменять их и подставлять друг в друга в любых конфигурациях)
```

## ПРИНЦИП 5: РОМБОВИДНАЯ ИЕРАРХИЯ МИ (Разделение на Управление и Механику)

В Модульной Иерархии должно быть четкое разделение на Управление и Механику. Вся Механика — внутри, состоит из атомарного минимума, максимально статична и не переписывается без острой необходимости. Управление — внешне, управляет атомарными возможностями максимально гибко и может программироваться внешними Вертикальными наслоениями.

Структура Ромба:

        🔺 ВЕРХНЯЯ ТОЧКА: Программа-Слой Рандомного Управления
        (сведение всех параметров к единой точке)
                    ↑
                    |
            ВЕТВЛЕНИЕ ВВЕРХ: Слой Управления (Параметры и Паттерны)
        (много параметров из ОДНОГО места)
                    ↑
                    |
        🔻 НИЖНЯЯ ТОЧКА: Атомарная Механика (Статика)
        (базовая механика, точка внизу ромба)

### 🔻 Нижняя точка Ромба: Атомарная Механика

Фундамент системы. Здесь нет ни капли "творчества" или "случайности". Это чистая физика и математика.
Свойства:

✅ Статична — протестирована и не переписывается без крайней нужды
✅ Атомарна — минимальный набор функций
✅ Устойчива — использует Принцип 5 (нулевая сигнатура + сеттеры, то есть классическое разделение на Данные и Поведние по МИ, но в рамках одного её микро-уровня)

Пример из музыкального проекта:

```python
# МЕХАНИКА (не переписывается!)
class JazzSynth:
    """Физика звука: фазовые накопители, ADSR, защита от щелчков"""
    def play_chord(self, frequencies, duration):  # Нулевая сигнатура
        # Чистая механика синтеза
        pass

class JazzGenerator:
    """Математика нот: частоты, интервалы, кварто-квинтовый круг"""
    def build_chord(self, octave, tonic_note, chord_type):
        # Чистая математика аккордов
        pass
```

### Ветвление вверх: Слой Управления

Дергаем за рычаги механики. Здесь живут Паттерны (генераторы тембров, логика морфинга в музыкальном примере).

Свойства:

✅ Гибко — можно добавлять новые паттерны без изменения Механики
✅ Вертикальные наслоения — новые поведения добавляются как новые слои (Паттерн, примененный к паттерну)
✅ Не знает, как работает Механика — только что нужно изменить

Пример:

```python
# УПРАВЛЕНИЕ (можно расширять бесконечно)
class Env(Pattern):
    """Огибающая ADSR"""
    def evaluate(self, t):
        return self.a * t  # Упрощенно

class Sine(Pattern):
    """Синусоидальное колебание для вибрато"""
    def evaluate(self, t):
        return math.sin(2 * math.pi * self.freq * t)

# Новый паттерн - не ломает Механику!
class VinylNoise(Pattern):
    """Эффект винилового шума"""
    def evaluate(self, t):
        return random.gauss(0, 0.1)
```

Все, что только можно следуюет делать открыто внешне задаваемым параметром, если только это не исключительно внутри-механическая константа. Определить, стоит ли выносить параметр во внешнее управление или оставить константой, очень просто: если от того, что мы его НЕ вынесем, механика вдруг сломается - мы его оставляем внутри. И ТОЛЬКО в этом случае!

### 🔺 Верхняя точка Ромба: Программа-Слой Рандомного Управления

Это "Мозг" или "Дирижер". Принимает решения: когда сменить тональность, как быстро морфить тембр, какой паттерн темпа применить.

Свойства:

✅ Сводит все параметры воедино
✅ Оркестрирует все слои Управления
✅ Генерирует случайность в рамках заданных правил

Пример:

```python
# ГЛАВНЫЙ ЦИКЛ (Кондуктор)
def run_jazz_cycle(key, key_mood, tempo_tick):
    """Оркестрация: собирает все параметры и отдает их в Механику"""
    # 1. Решает, какой аккорд играть
    # 2. Выбирает паттерны для голосов
    # 3. Обновляет темп
    # 4. Отдает всё в synth.play_chord()
    pass
```

В чем бонус над ООП?

❌ Проблема ООП (ромбовидное наследование):

```python
# В ООП мы бы создали:
class JazzChord:
    pass

class MorphingChord(JazzChord):  # Наследование
    pass

class RandomMorphingChord(MorphingChord, JazzChord):  # Ромбовидное наследование!
    # Проблема: изменение темпа ломает морфинг тембра!
    pass

✅ Решение МИ (Ромбовидная Иерархия):

# В МИ каждый слой имеет свою четкую роль:
# 1. Механика (низ) - не трогать! (без крайней нужды)
# 2. Паттерны (ветвление) - добавлять новые
# 3. Главный цикл (верх) - оркестрировать

# Изоляция ответственности:
# - Если звук "трещит" из-за резкого начала звука → чиним jazz_synth.py (Механику, физику)
# - Если музыка "скучная" → меняем веса в паттернах (Управление)
# Слои НЕ пересекаются!
```

Ключевые преимущества Ромбовидной Иерархии:

✅ Не запутаться при написании — каждый слой иерархии в Ромбе имеет свою четкую роль
✅ Дописывать любые фичи, не ломая программу — новые паттерны добавляются в слой Управления, не затрагивая Механику
✅ Безопасность для ИИ — жесткие Сигнатуры между Управлением и Механикой не дадут ИИ-агенту сломать ядро
✅ Бесконечная расширяемость — хочешь добавить "эффект винилового шума"? Создай новый паттерн VinylNoise и подмешай его в volume_pattern. Механика даже не узнает, что изменилось.

⚠️ ВАЖНО:
Ромбовидная Иерархия МИ — это НЕ ромбовидное наследование в ООП! Это иерархия по применимости, где все модели на одном уровне равны, но организованы в структуру Ромба для ясности архитектуры.

## ПРИНЦИП 6: МЕТОД ГИБКОГО ПЕРЕПИСЫВАНИЯ ЯДРА

Принцип Нулевой Сигнатуры Функции Запуска:

Каждая модель (особенно Механика) содержит функции двух разных видов:
Одна функция на запуск — чистая механика в действии
Много функций на параметры — по одному сеттеру на каждый параметр.

✅ ПРАВИЛО:

Функция запуска имеет НУЛЕВУЮ (минимальную) сигнатуру — только обязательные параметры, без которых модель не может работать (по возможности избегать!)
Все остальные параметры передаются через сеттеры до вызова функции запуска. В случае пропуска сеттера (забыли или еще не дописали) Модель автоматически прдустанавливает дефолтное значение параметра. Таким образом, даже при желании расширить сигнатуру Механики, она меняется гибко и неявно, а старая программа не падает с ошибкой.

```python
        """Устанавливает уровень реверберации"""
        self._reverb = value
    
    def play_chord(self, frequencies, duration_sec):
        # Сигнатура НЕ изменилась!
        # Используем self._reverb внутри
        pass

# Внешний код НЕ ломается!
# Если не вызвали set_reverb - используется дефолт 0.0 (реверберация выключена)
```

Результат: ✅ Внешний код работает без изменений. В худшем случае — звучит как раньше (реверберация выключена).

### 🛡️ Автоматические Дефолтные Значения

Критически важное правило:

Класс Модели должен автоматически устанавливать дефолтное значение каждого параметра, если он не передан.

Почему это важно?

1. Защита от невнимательности: Если забыли вызвать сеттер — модель работает с дефолтом
2. Устойчивость к изменениям: При добавлении нового параметра старый код продолжает работать

В худшем случае: Программа работает, но звучит/выглядит не так, как нужно (но не падает!)

Преимущества Метода:

1. Абсолютная устойчивость Механики
Функция запуска никогда не меняет сигнатуру
Добавление параметра = добавление сеттера
Внешний код не ломается

2. Разделение Данных и Поведения внутри Модели
Данные: сигнатура параметров (сеттеры)
Поведение: функция запуска (без жесткой сигнатуры ради гибкости)
Даже внутри нижней точки Ромба царит полная МИ!

3. Безопасность для ИИ-агентов
ИИ может добавлять новые сеттеры, не ломая существующий код
ИИ может переписывать внутреннюю логику, не трогая сигнатуру
Ошибки ИИ приводят к изменению поведения, но не к падению программы

4. Вертикальные наслоения безопасны
Можно добавить новый параметр тембра, новый эффект, новую модуляцию
Это не затронет существующий код
Старый код продолжит работать с дефолтными значениями новых параметров

5. Простота тестирования
Можно тестировать функцию запуска с дефолтными параметрами
Можно тестировать каждый сеттер отдельно
Можно тестировать комбинации параметров
