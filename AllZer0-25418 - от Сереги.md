## 1. Введение

### 1.1. Цель и формат документа
Документ описывает архитектуру, функциональность и требования к языку Zer0; изложение идёт от общего к частному. Термины помечены ссылками `[терм. N]` с номерами страниц; из глоссария можно перейти к первому упоминанию термина.

### 1.2. Целевая аудитория
Разработчики, реализующие интерпретацию Zer0, расширяющие язык или использующие его.

### 1.3. Обзор языка Zer0
Zer0 — минималистичный язык обработки строк, основанный на заменах с использованием карточек. Строго говоря, это язык не столько программирования, сколько перевода; он может служить основой для создания DSL, причём проектирование и реализация могут идти экспериментально одновременно.

#### 1.3.1. Для кого нужен Zer0
Для разработчиков, работающих с текстовыми данными и нуждающихся в гибком инструменте сложных замен и преобразований:
- обработка логов, трансформация данных, парсинг текстовых форматов;
- создание DSL с гибкими правилами замены;
- автоматизация обработки текстовых данных в исследовательских задачах.

#### 1.3.2. Сила и область применения
Сила Zer0 — минимализм и гибкость: пользователь полностью задаёт преобразования и не ограничен предопределёнными командами. В языке нет встроенных реализованных команд; исходно он оперирует только связями между пользовательскими командами. Поэтому язык рассчитан на высокую кастомизацию и универсальность.

#### 1.3.3. Практические задачи
1. Трансформация данных: код → UML, CSV → JSON, синтаксис DSL → уже существующий язык/формат без проектирования нового интерпретатора; обработка логов и извлечение ключевой информации.
2. Парсинг нестандартных текстовых структур и извлечение данных из шаблонов.
3. Автоматизация: генерация отчётов и замена шаблонов в документах.
4. Создание специализированных DSL.

#### 1.3.4. Философия Zer0
Философия — минимализм и максимальная гибкость. Zer0 отчасти сравнивается с расширенными регулярными выражениями и с минималистичным B**F, но принципиальное отличие — причина минимализма: у Zer0 нулевое количество встроенных команд. Пользователь определяет правила замен; они могут принимать форму произвольных грамматик.

**FLOM:**
1. **F — Flexibility (гибкость).** Не требуется подбирать язык под задачу и изучать его ограничения: достаточно задавать связи между карточками. При желании на Zer0 можно создать Тьюринг-полную грамматику в нужной форме; это позволяет сосредоточиться на смысле, а не форме.
2. **L — Linkes (принцип связей).** Важны не сами команды, а связи между ними: они определяют интерпретацию команд в последовательностях и порядок замен.
3. **O — Ontological Maximalism (онтологический максимализм).** Всё, что вводит пользователь, по умолчанию считается корректным; результат ошибки относится к действиям пользователя. Программист получает максимальную свободу, но может ограничить её в своей программе перевода.
4. **M — Minimalism (минимализм).** Нет встроенного перечня команд; пользователь определяет их «мимикрию». Можно комбинировать обычные значения, самоссылки, шаблонные значения и айдишники.

## 2. Архитектура языка Zer0

Работу можно сравнить с преобразованием символов на ленте или, по аналогии из документа, с заполнением пустых мест в формуле коммутаторами/конжугатами при сборке Twisty Puzzle. Условный алгоритм:
1. Есть карточки с двумя сторонами; на стороне значений фактически может быть несколько значений.
2. Есть входная строка.
3. Алгоритм ищет карточки внутри строки, учитывая длину, близость вхождения и другие параметры.
4. Найденная карточка «переворачивается» на другую сторону, преобразуя строку.
5. Алгоритм решает, закончить ли преобразование или продолжить. Строка может иметь любой формат и размер. Гарантия остановки желательна, но в документе отмечается, что она сделала бы Zer0 Тьюринг-неполным из-за неразрешимости проблемы останова.

### 2.0.1. Основные компоненты
Zer0 состоит из пяти сущностей:
1. **Card (Карточка)** — хранит одно Имя и от 0 до N Значений; порядок ввода карт не имеет значения.
2. **Library (Библиотека, «Либа»)** — хранит взаимно видимые карточки; является неупорядоченным множеством.
3. **CardManager (Менеджер Карт)** — проверяет карточки и выполняет настроечные действия.
4. **Parser (Парсер)** — обрабатывает и преобразует входную строку по связям между карточками и возвращает строку плюс дополнительную информацию, включая лог замен.
5. **Logger (Логгер)** — логирует процесс парсинга.

### 2.0.2. Компоненты

#### Входная строка (`inp_str`)
Пустая или непустая строка из допустимых в выбранной кодировке символов. Теоретически Zer0 можно реализовать как логическую схему, работающую с сигналами 1 и 0; автор предполагает, что это может решить проблему времязатратности алгоритма.

#### Алгоритм преобразований
Алгоритм (Перевод) — процесс замен имён карт на значения, затем значений обратно на имена в другом порядке. Обратный этап иногда отсутствует. Структура связей между картами задаёт декларативную программу перевода; возможна и программа, сохраняющая строку неизменной.

#### Имя карточки (`card_name`)
Имя — пустая или непустая строка, используемая как ссылка в алгоритме и некоторыми специальными карточками CardManager. Внутри одной библиотеки каждое имя и значение уникально: пустое имя или значение может принадлежать только одной карточке либо ни одной.

#### Значение карточки (`value`, `val`)
Значение — то, на что меняется строка после обнаружения имени карты. Четыре типа:
1. `usual_vals` — обычные;
2. `selflink_vals` — самоссылки;
3. `templ_vals` — шаблонные;
4. `id_vals` — идентификаторы.

Технический алгоритм состоит из трёх этапов:
1. **Прямые замены.** Для всех типов, кроме шаблонов, ищется совпадающее значение и заменяется именем карты. Контекст сокращается, увеличивается или изменяется. Алгоритм может закончиться здесь.
2. **Шаблонные замены.** Ищутся только шаблонные значения и заменяются шаблонным именем; ссылки «перетасовываются» в другом порядке/контексте. После этого этапа обратные замены обязательны.
3. **Обратные замены.** Имена шаблонных ссылок заменяются их значениями; это финальный этап, после которого алгоритм заканчивается.

Значения карт служат буфером между исходным и конечным состояниями строки.

#### Ссылка (`reference`, `ref`)
Ссылка — внутренняя сущность, которую пользователь напрямую не вводит; её вычисляет CardManager из библиотеки. Она содержит имя конкретной карты и эволюционирующее значение. Реализация может хранить всю историю значений или только последнее.

Ссылки задают связи между карточками и являются буфером между состояниями строки до и после обратных замен, что поддерживает декларативность Zer0.

- **Имя ссылки** — полное точное вхождение имени карты, впервые помещённое в ссылку.
- **Значение ссылки** — текущее эволюционирующее значение/последняя подстрока, заменённая данной ссылкой.
- **Первичное значение ссылки** — подстрока, первой заменённая данной ссылкой.
- **Тип ссылки** — две ссылки одного типа имеют одинаковые имена; типы служат независимыми «хранилищами» для шаблонных замен.

Пример:
```text
card1_name = 'number'
card1_vals = ['3']
inp_str = '3+3'
→ 'number+number'
→ 'number*2'
→ '3*2'
```
То есть прямые замены создают ссылки, шаблон меняет их контекст, обратные замены восстанавливают первичные значения.

Для нескольких типов:
```text
card1_name = 'int'
card1_vals = ['3']
card2_name = 'float'
card2_vals = ['0.5']
inp_str = '3+0.5+3+0.5'
→ 'int+float+int+float'
→ '(int+float)*2'
→ '(3+0.5)*2'
```

### Типы значений карт

#### Самоссылки (`selflink_vals`)
Пустая или непустая строка, содержащая имя собственной карты. Используется для сокращения контекста и обработки повторяющихся паттернов; прямые замены могут быть рекурсивными.

Самоссылка должна содержать имя карты хотя бы один раз:
```text
card1_name = '<number>'
card1_vals = ['1', '2', '<number><number>']
inp_str = '1121'
→ '<number><number><number><number>'
→ '<number><number><number>'
→ '<number><number>'
→ '<number>'
```
Таким образом, большие повторяющиеся группы можно временно свести к одному объекту.

#### Шаблонные значения (`templ_vals`)
Пустая или непустая строка, содержащая хотя бы одну ссылку хотя бы одного вида, совпадающего с видами ссылок в имени карты. Шаблонное значение должно содержать ссылки и в самом значении, и в имени принадлежащей ему карты.

Шаблоны переставляют участки строки, сохраняя сами значения ссылок, но меняя порядок и контекст:
```text
card1_name = '<number>'
card1_vals = ['3']
card2_name = '<number>*2'
card2_templ_vals = ['<number>+<number>']

inp_str = '3+3'
→ '<number>+<number>'
→ '<number>*2'
→ '3*2'
```

В шаблоне могут участвовать несколько типов:
```text
card1_name = '<number>'
card1_val = '1'
card2_name = '<symbol>'
card2_val = 'x'
card3_name = '(<number>+<symbol>)*2'
card3_templ_vals = ['<number>+<number>+<symbol>+<symbol>']

inp_str = '1+1+x+x'
→ '<number>+<number>+<symbol>+<symbol>'
→ '(<number>+<symbol>)*2'
→ '(1+x)*2'
```

Ещё один пример:
```text
card1_name = 'int'
card1_vals = ['3']
card2_name = 'float'
card2_vals = ['0.5']
card3_name = '(int+float)*2'
card3_templ_val = 'int+float+int+float'

inp_str = '3+0.5+3+0.5'
→ 'int+float+int+float'
→ '(int+float)*2'
→ '(3+0.5)*2'
```

Самоссылки и шаблоны вместе позволяют работать не только с конкретными значениями, но и с группами объектов:
```text
card1_name = '<number>'
card1_vals = ['1', '<number><number>']
card2_name = '<number>*2'
card2_templ_val = '<number>+<number>'

inp_str = '11+11'
→ '<number><number>+<number><number>'
→ '<number>+<number>'
→ '<number>*2'
→ '11*2'
```
Аналогично `111+111 → 111*2` и `11111+11111 → 11111*2`.

**Коллизия.** Если в шаблоне две ссылки одного типа имеют разные первичные значения, обратная замена неоднозначна:
```text
card1_name = '<number>'
card1_vals = ['1', '2']
card2_name = '<number>*2'
card2_templ_vals = ['<number>+<number>']

inp_str = '1+2'
→ '<number>+<number>'
→ '<number>*2'
→ '?*2'
```
Следуют три утверждения:
1. Коллизия — невозможность однозначно выбрать первичное значение для обратной замены.
2. Шаблоны с разными первичными значениями ссылок одного типа вызывают коллизию.
3. Шаблоны без коллизии имеют одинаковые первичные значения ссылок каждого типа.

Шаблон может одновременно быть самоссылкой:
```text
card1_name = '<number>'
card1_val = '3'
card2_name = '<number>*2'
card2_templ_val = '(<number>*2)'
inp_str = '(3*2)'
→ '(<number>*2)'
→ '<number>*2'
→ '3*2'
```

#### Идентификаторы (`id_vals`)
Идентификатор — самоссылка, участвующая в результатах парсинга обеих половин хотя бы одного шаблона. В документе он вводится как дополнение, необходимое для Тьюринг-полноты: шаблоны классифицируют типы ссылок, но не могут переставлять значения одного типа при разных первичных значениях без коллизии.

Айдишники позволяют оперировать ссылками одного типа с разными значениями. Пользователь может задавать их грамматику согласно FLOM.

Условия перераспределения самоссылки в `id_vals`:
1. она встречается в результате парсинга хотя бы одного шаблонного значения;
2. она же встречается в результате парсинга имени карты, содержащей это шаблонное значение.

- **Имя айдишника** — результат парсинга подстроки шаблона (имени и значения), на которую заменяется подстрока входной строки; технически это второе значение ссылки после первичного.
- **Тип айдишника** — тип ссылки, заменившейся на него при прямой замене.
- **Значение айдишника** — значение ссылки, на которое айдишник заменяется при обратной замене.

Пример простого swap:
```text
card1_name = '<number>'
card1_vals = ['1', '2']
card_val = ['<number<number>']
card2_name = '<number1>+<number2>'
card2_templ_vals = ['<number2>+<number1>']

inp_str = '1+2'
→ '<number>+<number>'
→ '<number1>+<number2>'
→ '<number2>+<number1>'
→ '2+1'
```
Парсер помнит, какое значение скрыто под каждым айдишником, но считает их ссылки однотипными, поэтому коллизии нет.

Другой синтаксис той же идеи:
```text
card1_name = 'number'
card1_vals = ['1', '2']
card_val = ['number.number']
card2_name = 'number.1+number.2'
card2_templ_vals = ['number.2+number.1']

inp_str = '1+2'
→ 'number+number'
→ 'number.1+number.2'
→ 'number.2+number.1'
→ '2+1'
```

#### Обычные значения (`usual_vals`)
Пустая или непустая строка, определяемая исключением: это не самоссылка, не шаблон и не идентификатор. Используется для простых замен и не содержит ссылок на себя или другие карточки.
```text
card1_name = '<number>'
card1_usual_vals = ['1', 'two']
```

### Упражнения и ответы
1. Для `card1_name = '<number>'`, `card1_?val = ['<number+number>']`: `? = usual`; изменение, необходимое для самоссылки, — сделать в значении полное вхождение имени `<number>`.
2. Для `card1_name = '<number>'`, `card1_?val = ['<number>number>']`: `? = selflink`.
3. Для `card1_name = '<number*<number'`, `card1_?val = ['<number^2']`: `? = usual`.
4. В упражнении с `card1_name = '<number'`, значениями `1,2` и `card2_name = '<number*<number'`, `card2_?val = ['<number^2']`, типы: значения карты 1 — `usual`, значение карты 2 — `templ`. Чтобы карта 2 стала шаблоном, достаточно одной замены `<number` → `<number>` в нужном месте; документ перечисляет допустимые позиции.
5. Для `card1_name = '<number>'`/`['1','2']`, `card2_name = '<symbol>'`/`['a','z']`, `card3_name = '<number>+<number>'`/`['<symbol>+<symbol>']`: все три значения — `usual`.
6. Для `card1_name = '<number1>'`/`['1']`, `card2_name = '<number2'`/`['2']`, имя карты 3 нужно заполнить так, чтобы в нём и значении присутствовали ссылки `<number1>` и `<number2>`; при отсутствии одной из них карта 3 не станет шаблоном. Ответ указывает, что число возможных вариантов зависит от расстановки этих имён и завершается условием `>= 0`.
7. Для:
```text
card1_name = 'num'
card1_vals = ['0', '3', 'num(num)']
card2_name = 'num(1)+num(2)'
card2_vals = ['num(2)+num(1)']
```
`0` и `3` — `usual`, `num(num)` — `selflink`, значение карты 2 — `templ`. Чтобы получить айдишник, самоссылка `num(num)` должна появляться после парсинга и имени, и шаблонного значения карты 2; тогда `num(1)` и `num(2)` становятся однотипными айдишниками, сохраняющими разные значения.

### Алгоритм Парсера / CardManager

**CardManager:**
- проверяет корректность карточек;
- строит связи между карточками, вычисляя ссылки;
- обрабатывает и деформирует айдишники, уточняя их внутреннюю структуру;
- документ оставляет дополнительные обязанности как `...`.

**Функциональные требования к обработке строк:**
- замена обычных значений;
- замена самоссылок;
- замена шаблонных значений;
- замена айдишников;
- обратные замены.

**Логирование:** формат лога — JSON.

## 7. Глоссарий

| Термин | Сжатое определение |
|---|---|
| Карточка (Card) | Хранит одно имя и 0–N значений; порядок ввода карт не важен. |
| Библиотека (Libruary) | Неупорядоченное множество взаимно видимых карточек. |
| CardManager | Управляет и проверяет карточки, вычисляет связи и настраивает айдишники. |
| Parser | Выполняет преобразования и возвращает строку и лог замен. |
| Logger | Логирует процесс парсинга. |
| Входная строка (`inp_str`) | Пустая или непустая строка из допустимых символов выбранной кодировки. |
| Алгоритм / Перевод | Замены имён карт на значения и затем значений на имена в другом порядке; структура связей задаёт декларативную программу. |
| Имя (`name`) | Строка, используемая как ссылка при преобразовании. |
| Значение (`value`, `val`) | То, на что меняется строка после обнаружения имени карты. |
| Прямые замены | Замены по всем типам, кроме шаблонов: совпавшее значение → имя карты; алгоритм может закончиться здесь. |
| Шаблонные замены | Шаблонное значение → шаблонное имя; переставляют ссылки и требуют последующих обратных замен. |
| Обратные замены | Шаблонные имена → значения; финальный этап, после которого алгоритм заканчивается. |
| Ссылка (`ref`) | Внутренняя сущность из имени карты и эволюционирующего значения; вычисляется CardManager. |
| Имя ссылки | Полное точное вхождение имени другой карты, впервые помещённое в ссылку. |
| Значение ссылки | Текущее/последнее значение подстроки, заменённой ссылкой. |
| Первичное значение ссылки | Значение, первым заменённое ссылкой. |
| Тип ссылки | Общий тип ссылок с одинаковыми именами. |
| Самоссылка (`selflink_vals`) | Значение, содержащее имя собственной карты; сокращает контекст. |
| Шаблон (`templ_vals`) | Значение, содержащее ссылку соответствующего вида и связанное с именем карты; переставляет ссылки/контекст. |
| Коллизия | Невозможность однозначно выбрать первичное значение при обратной замене. |
| Идентификатор (`id_vals`) | Самоссылка, участвующая в парсинге обеих половин хотя бы одного шаблона; используется для дополнения Zer0 до Тьюринг-полноты. |
| Имя айдишника | Результат парсинга подстроки шаблона, на которую заменяется входная подстрока; второе значение ссылки после первичного. |
| Тип айдишника | Тип ссылки, заменившейся на айдишник при прямой замене. |
| Значение айдишника | Значение ссылки, на которое айдишник заменяется при обратной замене. |
| Обычное значение (`usual_vals`) | Значение, не являющееся самоссылкой, шаблоном или идентификатором; используется для простых замен. |


## Приложение A. Технические позиции ссылок из исходных примеров

Ниже сохранены технические позиции `ref`, которые были вынесены из основного повествования для компактности. В исходнике эти поля оговариваются как временные; в дальнейшем за позицию должен отвечать лог-файл.

```text
//ref1 = {name == ‘number’, pos == 0}
//ref2 = {name == ‘number’, pos == 7}

//ref1(type1) = {name == ‘3’, pos = [0,6]}
//ref2(type2) = {name == ‘0.5’, pos = [2,8]}

//ref1(type1) = {name == ‘<number>’, pos == 0}
//ref2(type1) = {name == ‘<number>’, pos == 9}

//ref1(type1) = {name == ‘<number>’, pos == 0}
//ref2(type2) = {name == ‘<symbol>’, pos == 10’}
//ref3(type2) = {name == ‘<symbol>’, pos == 18}
//ref4(type2) = {name == ‘<symbol>’, pos == 27}

//ref1(type1) = {name == ‘int’, pos == 0}
//ref2(type1) = {name == ‘int’, pos == 10}
//ref3(type2) = {name == ‘float’, pos == 4}
//ref4(type2) = {name == ‘float’, pos == 14}

//ref1(type1) = {name == ‘<number>’, pos == 0}
//ref2(type1) = {name == ‘<number>’, pos == 9}

//ref1(type1) = {name == ‘<number>’, pos == 0}
//ref2(type1) = {name == ‘<number>’, pos == 9}

//ref1(type1) = {name == ‘<number>’, pos == 0}
//ref2(type2) = {name == ‘<number>*2’, pos == 1}
```

> **FLAG:** В исходном PDF некоторые из этих строк имеют очевидные опечатки/несогласованность кавычек. Они сохранены максимально близко к исходнику, а не исправлены.

## Приложение B. Примечание об исходном PDF
